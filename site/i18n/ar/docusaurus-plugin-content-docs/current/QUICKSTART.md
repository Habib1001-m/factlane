# البدء السريع

يشرح هذا الدليل إعداد خادم FactLane MCP محلي وربطه بوكيل. الخادم **عملية stdio يبدأها MCP host**،
وليس خدمة ويب أو تطبيقًا تفاعليًا في الطرفية. وهو يخزّن حقائق محدودة، لا نصوص المحادثات.

## كيف يبدو النجاح

في الإعداد الأول، اجعل الهدف محدودًا. تكون قد انتهيت عندما:

1. يستطيع MCP host المتوافق تشغيل FactLane؛
2. تظهر أدوات FactLane الخمس بالضبط؛
3. ينجح طلب `memory_status` للقراءة فقط ضمن نطاق دقيق.

ابدأ بوضع القراءة فقط. لا تفعّل كتابة Candidate إلا بعد نجاح الاتصال الأساسي.

## 1. اختر إصدارًا مسجلًا بدقة وتحقق من بيئة التشغيل

قبل تغيير الجهاز، افصل بين **الفحص** و**التعديل**. قراءة إعداد الـhost الحالي وهوية runtime المثبّتة
ومسارات التخزين ووثائق الإصدار هي أعمال للقراءة فقط. أما استنساخ الحزم أو تثبيتها، وسحب نموذج،
وتعديل إعداد الـhost، وتسجيل Skill، وإنشاء التخزين أو ترحيله، أو تغيير launcher profile فهي تعديلات
على البيئة وتتطلب صلاحية المشغّل/المستخدم المناسبة. إذا لم يملك الوكيل هذه الصلاحية، فعليه التوقف
عند الإرشاد وألا يدّعي أن تثبيتًا أو تهيئة قد حدثا.

استخدم [عمليات الإصدار](RELEASE_OPERATIONS.md) لتحديد خط الأساس المنشور المسجل في مرجع المستودع الذي تستخدمه. سجّل الـtag الدقيق مع commit/tree أو بصمات الحزم الموثقة هناك. لا تثبّت من فرع `main` المتغير، ولا تستنتج هوية إصدار من رقم الحزمة داخل نسخة مصدر عشوائية. قد تعلن نسخة تطوير رقم حزمة أحدث من دون أن يكون منشورًا.

عند التثبيت من source ذي إصدار محدد، اضبط `FACTLANE_TAG` على الـtag المنشور المذكور في Release
operations، ثم استنسخ ذلك الـtag بالضبط. يستخدم المثال POSIX shell؛ وفي PowerShell يمكن ضبط `$env:FACTLANE_TAG` وتمرير الوسم نفسه إلى `git clone --branch`:

```bash
FACTLANE_TAG='<published-tag-from-release-operations>'
git clone --branch "$FACTLANE_TAG" --depth 1 https://github.com/Habib1001-m/factlane.git
cd factlane
```

تحقق من commit/tree للـcheckout مقابل القيم المسجلة لذلك الـtag في Release operations قبل المتابعة.
إذا كنت تفضّل wheel أو source distribution منشورًا، فاتبع إجراء التثبيت المتحقق من الـdigest هناك
بدل تحويل مثال source-checkout بالتخمين.

ثبّت متطلبات CPython و[Ollama](https://ollama.com/) التي يحددها الإصدار المختار و[البيئة والتوافق](ENVIRONMENT.md). يستخدم مسار المستودع وملف القفل أدناه أيضًا [`uv`](https://docs.astral.sh/uv/)؛ أما تثبيت wheel منشورة فلا يتطلب `uv`. تحقق من مكتبة SQLite المرتبطة ببيئة Python نفسها التي ستشغّل FactLane:

يتطلب ملف المنتج المدعوم حاليًا SQLite runtime مرتبطًا بإصدار **3.42.0+**. ومع ذلك تحقّق من manifest
الإصدار المختار وحدود Environment بدل افتراض أن إصدارًا مستقبليًا سيحتفظ بالحد الأدنى نفسه.

```bash
uv sync --frozen
uv run python -c 'import sqlite3; print(sqlite3.sqlite_version)'
uv run factlane --help
uv run factlane --help-tools
```

يستخدم فحص SQLite أعلاه مفسّر المشروع. قد يعرض executable باسم `python` أو `sqlite3` على مستوى
النظام إصدارًا *مختلفًا*. إذا كان runtime المرتبط أقل من الحد الأدنى المطلوب للإصدار المختار، يعيد
FactLane الخطأ `BACKEND_COMPATIBILITY_MISMATCH` قبل إنشاء قاعدة البيانات أو فتحها. إصدار Python
وحده لا يحقق عقد التخزين.

### افحص التخزين الموجود قبل التشغيل

اختر مسار قاعدة البيانات المقصود **قبل** بدء runtime الجديد. إذا لم توجد قاعدة بيانات في هذا
المسار، فتابع بإعداد جديد للقراءة فقط. إذا كان التخزين موجودًا بالفعل، فلا تربط runtime المثبّت
حديثًا به لمجرد نجاح تثبيت الحزمة. سجّل أولًا هوية deployment/runtime الحالية ومصدر التخزين، ثم
استخدم قواعد التوافق والانتقال الخاصة بالإصدار المختار في
[عمليات الإصدار](RELEASE_OPERATIONS.md) لتحديد ما إذا كان يمكن فتح قاعدة البيانات تلك مباشرة أو
أنها تتطلب ترحيلًا صريحًا.

إذا تعذر إثبات التوافق، فتوقف. وإذا أعاد فحص التوافق أو startup محكوم الحالة
`MIGRATION_REQUIRED`، فأوقف الخدمة العادية بدل محاولة تجاوز الـhold. احتفظ بنسخة احتياطية
متحقق منها ومملوكة للمشغّل وفق الإجراء الخاص بالإصدار، ثم اتبع تعليمات الترحيل والتراجع في
Release operations حرفيًا. لا تسمح لتشغيل MCP العادي بأن ينفذ ترحيل التخزين أو يخترع إجراءً له.

## 2. ثبّت نموذج تضمين مدعومًا

اختر embedding profile مدعومًا من [البيئة والتوافق](ENVIRONMENT.md)، وثبّت النموذج الدقيق الذي
يتطلبه ذلك الملف، ثم شغّل خدمة Ollama المحلية بالطريقة المعتادة لتثبيتك. لا تخمّن زوج
profile/model من مثال قديم. يجب أن تتطابق هوية النموذج وأبعاده وسعة إدخاله مع الملف المختار. بصمة النموذج المرصودة من بيانات منشأ وقت التشغيل، وليست وحدها مفتاح قبول الملف. ولا ينزّل FactLane نموذجًا أو يستبدله تلقائيًا.

استخدم نقطة النهاية وحدود المزوّد الموثقة للإصدار المختار. في مصدر التطوير الحالي، يجب أن يكون عنوان Ollama الأساسي عنوان HTTP بـloopback literal دقيق، ويعطّل مسار طلبات FactLane وراثة إعدادات proxy المحيطة وإعادة التوجيه. لا تضف نقطة embedding بعيدة أو fallback ما لم يدعمها إصدار مستقبلي صراحة.

## 3. اختر ملف تعريف التشغيل

يتطلب تشغيل خادم FactLane ثلاثة عناصر إعداد: `--db` لملف SQLite المحلي، و`--host-id` كتسمية
ثابتة غير سرية للـlauncher، وembedding `--profile`. اختر الملف من وثائق Environment الحالية
بدل الاعتماد على قيمة افتراضية ضمنية أو تاريخية.

للاتصال الأول، أبقِ الـlauncher للقراءة فقط بحذف `--write-profile`. يستخدم المثال متعدد الأسطر استمرار أسطر POSIX shell؛ ويمكن في PowerShell وضع الوسائط نفسها في سطر واحد أو استخدام صيغة الاستمرار الخاصة به:

```bash
FACTLANE_PROFILE='<supported-profile-from-environment>'
uv run factlane \
  --db ./factlane.sqlite3 \
  --profile "$FACTLANE_PROFILE" \
  --host-id example-host
```

لا تشغّل هذا الأمر كأنه REPL؛ اضبط MCP host ليبدأه عبر stdin/stdout. وإذا كان الـhost يبدأ FactLane
من working directory آخر، فاستخدم مسارات **مطلقة** للـexecutable وقاعدة البيانات.

حذف `--write-profile` يبقي الاتصال الأول للقراءة فقط. لا تضف write profile قبل نجاح فحص الاتصال
للقراءة فقط في الخطوة 4.

### Codex (مضيف stdio مختبَر)

مثال لإدخال `~/.codex/config.toml`:

```toml
[mcp_servers.factlane]
command = "/absolute/path/to/factlane/.venv/bin/factlane"
args = [
  "--db", "/absolute/path/to/state/factlane.sqlite3",
  "--profile", "<supported-profile>",
  "--host-id", "codex"
]
enabled = true
```

على Windows الأصلي، استخدم مسارات Windows الفعلية للتنفيذ وقاعدة البيانات بدل مسارات POSIX، مثل `C:\path\to\venv\Scripts\factlane.exe` و`C:\path\to\state\factlane.sqlite3`.

أعد تحميل إعداد MCP في نسخة Codex المثبّتة لديك وتأكد من ظهور أدوات FactLane الخمس. ينبغي أن
يتبع استخدام الوكيل لهذه الأدوات [using-factlane Skill](USING_FACTLANE_SKILL.md)
المحمولة، والمسجّلة عبر آلية Skill التي يدعمها الـhost. يتضمن توزيع Skill الملف `SKILL.md`
والمرجع `references/host-bootstrap.md`. وجود الملفات يثبت وجود bytes الخاصة بالـSkill فقط؛ ولا
يثبت أن الـhost سجّلها أو اكتشفها أو حمّلها. أبقِ الحالات `present` و`registered`
و`discoverable` و`loaded` كحقائق منفصلة ملحوظة، واستخدم مرجع bootstrap للأدلة المطلوبة لكل
حالة.

### Hermes (مضيف stdio مختبَر)

مثال `~/.hermes/config.yaml`:

```yaml
mcp_servers:
  factlane:
    command: "/absolute/path/to/factlane/.venv/bin/factlane"
    args:
      - "--db"
      - "/absolute/path/to/state/factlane.sqlite3"
      - "--profile"
      - "<supported-profile>"
      - "--host-id"
      - "hermes"
```

على Windows الأصلي، استخدم مسارات Windows المقابلة للتنفيذ وقاعدة البيانات. لا تمرر مسار WSL إلى وقت تشغيل Windows الأصلي.

أعد تحميل إعداد MCP في Hermes وتحقق من tool discovery. الـSkill المحمولة موجودة في source وpackage
artifacts الخاصة بـFactLane، لكنها **لا تُسجّل تلقائيًا** لدى أي host بمجرد تثبيت wheel. استخدم
آلية Skill التي يدعمها الـhost، وبلّغ `present` و`registered` و`discoverable` و`loaded`
كحالات منفصلة ملحوظة.

### عميل MCP آخر

اضبط executable نفسه، `factlane`، والوسائط نفسها في عميل يدعم MCP محليًا قائمًا على أوامر
**stdio**. امنح كل host موثوق تسمية `--host-id` ثابتة مناسبة. العملاء الآخرون متوافقون من حيث
البروتوكول من حيث المبدأ، لكن لم يتم تأهيلهم جميعًا على حدة. HTTP/SSE وStreamable HTTP غير
مدعومين في الخادم الحالي.

## 4. تحقق من الاتصال قبل الكتابة

ينبغي أن يكتشف MCP host الأدوات التالية بالضبط:

```text
memory_search
memory_get
memory_store
memory_update
memory_status
```

مجرد ظهور `memory_store` أو `memory_update` لا يمنح صلاحية استخدامهما؛ فما زال launcher
profile يتحكم في الكتابة. اطلب من العميل استدعاء `memory_status` ضمن نطاق دقيق. وللفحص في
GLOBAL_USER من دون الحاجة إلى project ID:

```json
{"request":{"scope":"GLOBAL_USER"}}
```

إذا نجح الطلب، فقد اكتمل هدف التشغيل الأول الآمن: يستطيع الـhost تشغيل FactLane، ويظهر سطح الأدوات
العام، ويمكن لطلب للقراءة فقط عبور مسار runtime المضبوط.

### ملاحظات الهوية والاسترجاع

تصبح الأمثلة التالية مهمة عندما تتجاوز فحص الاتصال الأول.

في بحث PROJECT **غير مربوط**، قد يبدو الطلب هكذا:

```json
{
  "request": {
    "scope": "PROJECT",
    "project_id": "example-project",
    "intent_class": "CURRENT_PROJECT_STATE",
    "query": "What release constraints are recorded?",
    "retrieval_mode": "CURRENT",
    "retrieval_mode_kind": "KEYWORD"
  }
}
```

عندما يربط المضيف الموثوق هوية مشروع أو سير عمل أو بيئة أداة، **احذف المعرّف المربوط المقابل من الطلب**. يضيفه FactLane عند البوابة؛ ويجب أن تطابق أي قيمة صريحة لـ`project_id` أو `workflow_id` أو `agent_id` القيمة المربوطة، وإلا يفشل الطلب مغلقًا مع `BOUND_CONTEXT_IDENTITY_MISMATCH`. يختلف `CROSS_PROJECT_WORKFLOW`: فهو يمنع وجود *كل* مفاتيح
هوية project وworktree وworkflow وagent، ولا يبحث في كل المشاريع تلقائيًا.

في بحث `CURRENT` الدلالي أو hybrid، يختار FactLane عبر مصادر provenance مخزنة ومتحقق منها
ومتميزة قبل ملء مواضع بمصادر مكررة. يبقى أعلى نتيجة مؤهلة محفوظًا، ولا يعاد كتابة relevance
scores المعادة، بينما تحافظ عمليات exact وkeyword-only و`REVIEW_HISTORY` على دلالات ترتيبها
الحالية.

تستخدم حالات الفشل المحكومة في FactLane قناة نتائج MCP نفسها المستخدمة للنجاح، وتعيد
`status=BLOCKED` مع `error_code` ثابت و`message` آمنة و`results` فارغة و
`audit.retryable`. تفرّع على `error_code` ولا تحلل نصوص الاستثناءات. وتظل الاستثناءات الداخلية
غير المتوقعة أخطاء transport لا نتائج FactLane محكومة.

## 5. فعّل كتابة Candidate فقط بعد نجاح القراءة فقط

العلم `--write-profile` هو **إعداد launcher موثوق**:

| Launcher profile | ما الذي يسمح به |
| --- | --- |
| محذوف / `read-only` | البحث والجلب والحالة؛ بلا تعديل للذاكرة. |
| `delegated-candidate` | يستطيع الوكيل العادي استخدام `memory_store` لإضافة `CANDIDATE`؛ ولا يستطيع التحقق من نفسه أو التحديث. |
| `owner-current`، `repo-verifier`، `automated-verifier` | ملفات مشغّل/متحقق موثوقة ومقيدة؛ لا تضبطها لوكيل عادي كي يحصل على صلاحية أعلى. |

موافقة المستخدم على المحتوى لا تغيّر صلاحية الوكيل العامل. ترقية Candidate هي عملية
`memory_update` موثوقة ومنفصلة. للموافقة على المحتوى مساران مدعومان: طلب صريح مثل «تذكّر هذا»،
أو حقيقة قابلة لإعادة الاستخدام يقترحها الوكيل ثم يصرح المستخدم بها صراحة. كلاهما يصرّح فقط
بمحتوى Candidate المحدود، وفق حدود runtime والخصوصية الفعالة؛ ولا يصرّح بتغيير launcher profile
أو التحول إلى verifier.

إذا كان يجب السماح للوكيل المتصل بإضافة **Candidates غير متحقق منها**، فأضف إعداد launcher
الموثوق:

```text
--write-profile delegated-candidate
```

يسمح هذا الملف لـ`memory_store` بإضافة Candidate، لكنه **لا** يسمح للوكيل العادي بالتحقق من
مساهمته أو ترقيتها.

إذا لم يحتج الاتصال إلى إضافة ذاكرة، فاترك write profile محذوفًا/للقراءة فقط.

إذا لم يُعد البحث نتيجة، فلا تعامل ذلك كإذن لاختراع حقيقة. لإضافة Candidate حقيقية، راجع
`factlane --help-tools` أو مخطط MCP الحي لمعرفة حقول `source_provenance` و`freshness_policy`
و`memory_type` و`idempotency_key` المطلوبة كاملة. استخدم حقيقة واحدة محدودة وقابلة للإسناد،
لا transcript أو dump عشوائي لمجلد. إذا كانت الحقيقة المقترحة من الوكيل وليست طلبًا صريحًا من
المستخدم، فاعرض الحقيقة المحدودة واحصل على تفويض صريح قبل استدعاء `memory_store`. لا تنفّذ
تخزينًا تلقائيًا بعد انتهاء الدور.

المتحقق الموثوق الذي يراجع Candidate يستخدم `REVIEW_HISTORY` لفحصها و`memory_update` مع
`mode=REVERIFY` و`expected_revision` و`expected_record_id` الخاص بالـCandidate لترقيتها.
لا يملك الوكيل المفوّض صلاحية verifier حتى مع موافقة المستخدم في الدردشة. لا يستطيع `REVERIFY` تغيير هوية التناقض الخاصة بـCandidate. ينطبق `REPLACE` على ذاكرة منطقية Current مؤهلة؛ وليس مسارًا لتعديل Candidate. إذا كان Candidate خاطئًا ماديًا أو مصنفًا خطأ، فاتركه بلا ترقية؛ ويمكن لـOwner مباشر تنفيذ `REJECT` له، ثم يمكن تقديم Candidate المصحح والمحدود ومراجعته.

### مسار تحكم Owner موثوق اختياري

ينتهي مسار onboarding الطبيعي للوكيل عند أدوات MCP العامة الخمس أعلاه. قد تشحن بعض الإصدارات
المنشورة أسطح تحكم محلية للـOwner مثل `factlane-owner` أو `factlane-owner-webui`. تعامل معها
كـ**واجهات مشغّل موثوق اختيارية** فقط عندما يوثقها الإصدار المختار ويثبتها؛ ولا تفترض وجودها
من هذا البدء السريع.

لا ينشئ تحكم Owner أداة MCP سادسة. المشغّل المباشر `factlane-owner-webui` واجهة loopback، بينما دورة الحياة المُدارة `factlane ... webui` سطح مستقل تديره المنصة؛ ولا يمثل أيهما نقل MCP عبر HTTP. اربط
عمليات Owner بالنطاق الموثوق الدقيق، واستخدم inventory/detail الحالية أو ملاحظات conflict لإثبات
رقم `revision` وGroup CAS. لا تحاول عمليات lifecycle الخاصة بالـOwner من جلسة delegated-agent، ولا
تعتبر موافقة المحتوى في الدردشة صلاحية Owner أو صلاحية على مستوى الجهاز.

حيثما تكون مدعومة، فإن `REVOKED` و`REJECTED` حالتا lifecycle منطقيتان وليستا محوًا ماديًا.
Manual recheck وreadmission عمليتا Owner صريحتان، وليستا مراقبة مصدر في الخلفية أو database
restore أو إحياء لمحتوى أزيل عبر recovery. اتبع وثائق Owner والأمان الخاصة بالإصدار المختار
للحصول على الأوامر الدقيقة وحدود التعديل.

### التطوير الحالي: استخدام Owner Panel المُدارة

يصف هذا القسم **واجهة التطوير الحالية غير المنشورة**. ولا يجعل رقم package في مصدر التطوير إصدارًا منشورًا أو يحل محل مرجع الإصدار المسجل في [عمليات الإصدار](RELEASE_OPERATIONS.md).

على Linux، يتطلب إعداد Owner Panel المُدارة جلسة مستخدم غير root على مضيف `systemd` يعمل، مع توفر `systemctl` وCaddy وZenity وMozilla Firefox أو Firefox ESR وأداة NSS `certutil` عبر مسارات تنفيذية مطلقة. ويلزم `loginctl` أيضًا عندما تحتاج خطة الإعداد إلى تفعيل lingering للمستخدم. هذه متطلبات خاصة باللوحة المُدارة، وليست متطلبات إضافية لخادم MCP العادي عبر stdio.

تستخدم Owner Panel المُدارة أمر `factlane` الرئيسي:

```text
factlane setup webui
factlane doctor webui
factlane launch webui
factlane start webui
factlane status webui
factlane open webui
factlane stop webui
factlane restart webui
```

قبل إعادة تركيب المسارات المحلية يدويًا، استخدم `factlane doctor webui`. هذا سطح فحص للقراءة فقط: يعرض FactLane executable/interpreter المحسومين، وربط قاعدة البيانات/profile المُدار أو الـprofiles المدعومة عندما يكون الربط غير مهيأ، ومسار الـSkill المضمّن، ووجود مشغّل Owner Panel، وملاحظة الخدمة المُدارة، ووصفة argv محايدة للمضيف لتشغيل MCP بوضع read-only. لا يعدّل MCP host، ولا يسجل Skill، ولا يبدأ خدمة اللوحة، ولا يغير write profile، ولا يثبت model/package، ولا يرحّل التخزين. تبقى هوية MCP host بحالة `EXPLICIT_REQUIRED` ويبقى النطاق `EXPLICIT_PER_REQUEST`.

للفتح العادي بعد الإعداد، استخدم `factlane launch webui`. يفحص حالة الخدمة، ويبدأ الخدمة المُدارة عند الحاجة، ثم ينفذ مسار `open` الموثوق نفسه. وتظل أوامر `status` و`start` و`open` ذات المستوى الأدنى متاحة للتحكم الصريح في الخدمة. الإعداد إجراء منفصل يتطلب تأكيدًا صريحًا.

بعد نجاح الإعداد، يثبت FactLane أيضًا مشغّل Owner Panel للمستخدم الحالي. على Linux تكون هناك خانة تطبيق `.desktop` لا تفتح Terminal؛ وعلى Windows يُنشأ اختصار **FactLane Owner Panel** داخل Start Menu للمستخدم الحالي. كلاهما يعيد استخدام مسار `launch webui` الموثوق ولا يتجاوز ضوابط الخدمة أو المصادقة المُدارة.

على Linux، إذا لم يحدد الإعداد المُدار في التشغيل الأول ذاكرة بعد، يعرض setup shell الموثق الـprofiles المدعومة ومسار قاعدة بيانات محليًا مقترحًا وهوية Owner غير سرية مقترحة. يتحقق الربط من مسار قاعدة البيانات الدقيق وعقد التخزين الحالي وأي ربط embedding profile موجود قبل النشر. يظل storage v2 حد ترحيل صريحًا: يعيد الإعداد migration-required بدل إجراء الترحيل. يغير الربط الناجح `db`/`profile`/`host_id` فقط داخل الإعداد المُدار الخاص بالمالك، ويتحقق من النشر الذري، ثم يطلب إعادة تشغيل خدمة المستخدم الحالية. ولا يضبط هذا المسار هوية MCP host المنفصلة أو نطاقات طلباته.

على Windows x64/AMD64 الأصلي، يحفظ الإعداد المُدار حالة خاصة بالمالك تحت `%LOCALAPPDATA%\FactLane`، ويسجل مهمة Task Scheduler واختصار Start Menu للمستخدم الحالي، ويتطلب Mozilla Firefox للمتصفح المُدار. لا يوجد بديل تلقائي عبر Edge/Chrome. يستخدم FactLane ملف Firefox مُدارًا مخصصًا ومواد HTTPS محلية؛ لا تعطّل التحقق من الشهادات، ولا تستخدم ملف Firefox شخصيًا أو رايات تجاوز المتصفح، ولا تستبدل مسارات قاعدة البيانات بمسارات WSL/UNC.

بعد الاتصال، تضم قائمة التنقل الرئيسية **Overview** و**Memories** و**Review** و**Conflicts** و**Database** و**Agents** و**Activity** و**الإعدادات (Settings)**. تعرض **Activity** سجل العمليات ودورة الحياة المحلي القابل للتصفية. توجد Diagnostics محلية ومنقحة داخل **الإعدادات**؛ ولا يعني أي من السطحين رفع بيانات إلى جهة خارجية.

تبدأ **Memories** افتراضيًا باكتشاف للقراءة فقط على مستوى Owner عبر النطاقات المملوكة داخل قاعدة البيانات المحلية المحددة، لذلك لا تحتاج إلى معرفة معرّف النطاق قبل العثور على السجل. ويفتح **Review** أيضًا كقائمة Candidates على مستوى Owner. هذا التجميع وسيلة قراءة/اكتشاف للـOwner فقط؛ ولا يغير عقد MCP العام ذي الأدوات الخمس ولا يمكن إعادة استخدامه كتعديل عابر للنطاقات. عند اختيار سجل أو Candidate، ترتبط مسارات التعديل بالنطاق الدقيق لذلك السجل وتعيد جلب إثبات record/revision/Group-CAS الحالي قبل التنفيذ.

عند اعتماد Candidate، يستخدم المسار العادي حقل تاريخ/وقت محلي ويعرض منطقة المتصفح الزمنية. يحوّل FactLane القيمة مرة أخرى إلى عقد timestamp ذي المنطقة الزمنية المطلوب من backend. ولا يطلب نموذج المراجعة العادي منك كتابة record IDs أو revisions أو Group-CAS tokens؛ تبقى هويات التزامن هذه مشتقة من السجل الحالي المحدد. وتظل حقول provenance المتقدمة متاحة عندما يحتاج الدليل نفسه إلى تصحيح.

تتبع **Conflicts** القاعدة نفسها: تعرض محتوى الذكريات المتعارضة ودليلها بصياغة مفهومة، بينما تبقى هويات memory/record/revision/Group-CAS الدقيقة داخلية ويُعاد جلبها قبل الحسم. وإذا تغيرت مجموعة التعارض الدقيقة، تطلب اللوحة مراجعة جديدة بدل إعادة توجيه اختيار المالك بصمت.

تعرض صفحة Database عمليات قاعدة بيانات بحسب الإمكانات المتاحة، ومنها ملفات نسخ احتياطي صريحة، والتصدير/الاستيراد المنطقي، ومعاينات الاستعادة ومهامها، والعمليات التدميرية حيث تعلن المنصة دعمها. تبقى الحقائق المستوردة Candidates إلى أن تُراجع وفق الضوابط.

يمكن لـOwner المتقدم أيضًا تسجيل قاعدة بيانات محلية أخرى متوافقة لاستخدامها لاحقًا في تبديل منضبط:

```text
factlane register database <path>
```

يتحقق التسجيل من المسار المحلي ومن توافق عقد التخزين/profile الحالي، وينشئ حيازة مُدارة لقاعدة البيانات المسجلة؛ لكنه لا يبدّل قاعدة البيانات النشطة بنفسه ولا يعرّض مسارًا عشوائيًا يرسله المتصفح. ويستهلك تبديل قاعدة البيانات في Owner Panel قاعدة محلية متوافقة ومسجلة صراحة عبر حد الصيانة نفسه الموثق والمسبوق بالمعاينة.

تتطلب الاستعادة الكاملة لقاعدة البيانات والمحو الدائم معاينة دقيقة وحديثة، إضافة إلى موافقة منفصلة عبر آلية المنصة الأصلية على الإجراء الحساس قبل التنفيذ. في الاستعادة، أقرّ صراحة بأن حالة قاعدة البيانات النشطة ستُستبدل قبل طلب/استخدام تلك الموافقة. وفي المحو، اكتب نص التأكيد الدقيق الذي تعرضه المعاينة. إذا دخلت أي من العمليتين حالة recovery-required، فاحتفظ بهوية العملية والمعاينة نفسهما واحصل على موافقة حساسة جديدة للمحاولة التالية؛ لا تعِد استخدام grant مستهلكة. تستبدل الاستعادة حالة قاعدة البيانات النشطة وتبطل جلسات Owner القائمة بعد التفعيل؛ أعد الاتصال عبر المسار المُدار قبل المتابعة. يختلف المحو الدائم عن `REVOKE`/`REJECT` العاديين وعن مشغّل Recovery العام لحوادث الذاكرة الحساسة.

ترحيل storage-v2 → v3 منفصل أيضًا عن استعادة اللوحة. أوقف الخدمة العادية واستخدم `factlane-migrate-storage-v3` مع إجراء النسخة المتحقق منها قبل v3 والتراجع الموثق في [عمليات الإصدار](RELEASE_OPERATIONS.md). يتضمن مصدر التطوير الحالي مسار ترحيل وتراجع دقيق إلى ما قبل v3 على Windows x64/AMD64 الأصلي؛ وتبقى تعليمات الإصدار التاريخية للتنفيذ الأقدم مقصورة على POSIX لأن ذلك التنفيذ لم يتضمن مسار صيانة Windows.

يمكن لجلسة Owner صالحة الاستمرار بعد إعادة تحميل الصفحة: تستأنف اللوحة الجلسة القائمة وتدوّر رمز CSRF من دون إعادة ضبط مهلة الخمول أو العمر المطلق للجلسة. إذا كانت الجلسة غير صالحة أو منتهية، فارجع إلى مسار الاتصال المُدار. لا تنسخ محدد اتصال قديمًا أو تعِد تسليمه. يظهر تعارض pre-authentication كـ`PENDING_CLAIM_CONFLICT`؛ تخلّص من هذا التسجيل وابدأ عملية `factlane open webui` جديدة. تستخدم استجابات native control العادية حد 10 ثوانٍ، بينما تسمح تأكيدات enrollment/sensitive البشرية الصريحة بما يصل إلى 125 ثانية للاستجابة. يظهر انتهاء مهلة التأكيد كـ`CONTROL_UNAVAILABLE`، وليس كإذن لإعادة استخدام locator القديم.

لحدود المنصة ومتطلبات المتصفح، راجع [البيئة](ENVIRONMENT.md). ولحدود المصادقة والموافقة على الإجراءات التدميرية وRecovery الحساسة، راجع [الأمان](SECURITY.md).

## 6. الحدود والمراجع التالية

تقتصر الحقائق على 2,000 UTF-8 byte. FactLane ليس مفهرسًا لمحتوى خام أو نظام نسخ احتياطي مُدارًا ومستمرًا أو بوابة embedding بعيدة. يمكن لـOwner Panel إنشاء ملفات نسخ احتياطي محلية صريحة، لكن الاحتفاظ بها وسياسة النسخ الخارجية يظلان مسؤولية المشغّل. إعادة إنتاج هذا الملف النموذجي لا تثبت جودة اللغة أو production-scale
throughput لبياناتك. Sensitive-memory recovery إجراء منفصل بتفويض من المشغّل، **وليس** أداة MCP
عامة؛ راجع [الأمان](SECURITY.md) لحدود الثقة الخاصة بالاستعادة.

تابع إلى [أدوات MCP الخمس](TOOLS.md) للحصول على دليل الأدوات الموجه للمطورين.

للتقييم الأعمق، راجع [المعمارية](ARCHITECTURE.md) لتدفق البيانات الدقيق،
و[البيئة](ENVIRONMENT.md) لبيئة التشغيل والملفات،
و[عمليات الإصدار](RELEASE_OPERATIONS.md) للتثبيت/الترقية/التراجع المرتبط بالإصدار،
و[الأمان](SECURITY.md) لحدود الثقة والاستعادة. ويظل مخطط MCP الحي ومخرجات
`--help-tools` المرجع النهائي لتواقيع الطلبات والقيم المعدودة.
